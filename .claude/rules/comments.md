# 注释规范

## 核心原则

- **代码**负责说明"是什么 (What)"和"怎么做 (How)"
- **注释**专门说明"为什么 (Why)"

## 1. 代码即文档

- **命名表意**：使用精准的、描述性的词汇命名变量和函数（如用 `extract_data_from_db` 替代 `process_data`）
- **类型标注**：强制使用类型提示明确入参和出参，减少冗余文字解释

## 2. 标准化文档字符串

**适用范围**：所有对外暴露的 API、公共类、核心函数。

**必备结构**：

```python
def create_user(user_id: int, name: str) -> User:
    """创建新用户并写入数据库。

    Args:
        user_id: 用户唯一标识符。
        name: 用户显示名称。

    Returns:
        创建成功的 User 对象，包含数据库生成的字段。

    Raises:
        DuplicateUserError: 当 user_id 已存在时抛出。
    """
```

## 3. 精简行内注释

- **禁止废话**：绝不解释基础语法（如 `# 变量加一`）
- **解释妥协与特殊性**：专注解释反直觉的实现、复杂的业务限制或算法边界条件
- **标记待办**：使用 `# TODO:` 或 `# FIXME:` 标记临时方案或已知缺陷

```python
# ✅ 有价值的注释：解释为什么，而非是什么
# PostgreSQL 不支持直接类型转换，需要 USING 子句显式指定转换逻辑
op.execute("ALTER TABLE ... USING column::timestamp")

# ❌ 废话注释
i += 1  # i 加 1
```

## 4. 注释生命周期管理

- **清理废代码**：废弃代码直接删除，依赖 Git 溯源，禁止保留大段被注释的无用代码
- **同步更新**：每次修改代码逻辑时，必须同步更新或删除关联的旧注释，避免误导

## 违规模式检测

发现以下情况应立即指出并给出修复建议：

- 注释只是重复代码本身的含义（废话注释）
- 公共函数/类缺少 Docstring
- 代码逻辑已修改但注释未同步
- 保留了大段被注释掉的废弃代码
