# Handoff

跨会话零信息损失的工作移交机制。核心目标：让接手方读完文档后，不需要问任何问题就能继续工作。

## 设计原则

- **接手者视角**：所有内容围绕"接手方需要知道什么"来组织
- **可操作性**：每一条信息都应该能直接指导下一步行动
- **不遗漏上下文**：代码之外的决策背景、口头约定、踩过的坑都要记录
- **可验证**：接手方能通过文档中的步骤验证当前状态是否正确

## 触发场景

- 用户说"保存进度"、"移交"、"handoff"、"checkpoint"
- 上下文窗口接近上限，需要主动保存
- 当前任务阶段完成，需要记录状态后结束会话
- compress 后需要恢复完整上下文
- 长时间任务中途需要暂停

## 工作流程

### 1. 收集当前状态

在写入文档前，必须先收集以下信息：

```bash
# Git 状态
git branch --show-current
git log --oneline -5
git status
git diff --stat

# 如果有未提交的变更，查看具体内容
git diff
git diff --cached
```

### 2. 回顾工作上下文

回顾当前会话中的关键信息：

- 用户最初的需求是什么（原始表述）
- 实际执行过程中需求有没有变化或澄清
- 做了哪些技术决策，为什么
- 遇到了哪些问题，怎么解决的（或还没解决）
- 有没有发现但没处理的问题（技术债、潜在风险）

### 3. 提交未保存的变更

```bash
git status
# 如有变更，提交并推送
git add <相关文件>
git commit -m "wip: <当前工作简述>"
git push origin <branch-name>
```

### 4. 写入移交文档

根据场景选择写入 HANDOFF.md 或同时写入 CHECKPOINT.md。

文档写入位置：`workspace/` 目录。若不存在则创建。

### 5. 推送移交文档

```bash
git add workspace/HANDOFF.md workspace/CHECKPOINT.md
git commit -m "docs: 更新移交文档"
git push origin <branch-name>
```

## 场景处理

### 场景 A：主动保存（用户要求保存进度）

1. 收集 Git 状态和工作上下文
2. 提交并推送所有未保存的变更
3. 写入 `workspace/HANDOFF.md`（使用完整模板）
4. 如果上下文已经很长，额外写入 `workspace/CHECKPOINT.md`
5. 提交并推送移交文档
6. 告知用户：新会话中说"继续 `<分支名>`"即可恢复

### 场景 B：上下文紧张（主动触发）

1. 立即写入 `workspace/CHECKPOINT.md`（优先保证信息不丢失）
2. 如果还有余量，补充写入 `workspace/HANDOFF.md`
3. 提交并推送
4. 提醒用户上下文即将耗尽，建议开启新会话

### 场景 C：Compress 后恢复

1. 检查 `workspace/HANDOFF.md` 和 `workspace/CHECKPOINT.md` 是否存在
2. 优先读取 HANDOFF.md（信息更完整），CHECKPOINT.md 作为补充
3. 确认当前分支和 commit 状态与文档一致
4. 如果 commit 不一致，用 `git log` 检查是否有新的提交
5. 从"下一步行动"继续工作

### 场景 D：恢复会话（用户说"继续"）

1. 读取 `workspace/HANDOFF.md`（如有 CHECKPOINT.md 也一并读取）
2. 检查分支状态，确认与移交文档一致
3. 快速浏览关键变更文件，确认代码状态
4. 向用户汇报当前状态（一句话总结 + 下一步计划）
5. 等用户确认后，从"下一步行动"开始执行

## 写作要求

### 必须做到
- 所有描述必须具体，禁止使用"修改了一些文件"、"做了一些调整"这类模糊表述
- 文件路径必须完整准确
- 代码片段必须是实际代码，不是伪代码
- 决策记录必须包含"为什么"，不能只写"选了 A"
- 踩坑记录必须包含复现条件和解决方式

### 禁止出现
- "详见代码"（接手方就是因为看不懂代码才需要交接文档）
- "之前讨论过"（新会话没有之前的上下文）
- "应该没问题"（要么验证过写"已验证"，要么没验证写"未验证"）
- 没有上下文的缩写或代号（第一次出现必须写全称）
